    RL environment: can a shortcut score well?¶

    In one paragraph, for a non-engineer

    The product investigates a trade and publishes a finding. This page asks a harder question: could an investigator that cuts corners still look good? To find out, the same investigation loop is turned into a small practice environment with a scoring rule, and a handful of scripted shortcut strategies are run through it. Each one scores far below a proper investigation, and a test in CI keeps it that way. It is an extra on top of the surveillance product, not the product itself.

    Problem¶

    An insider-trading investigator can look right while cutting corners: skipping evidence, citing things it never retrieved, or asserting a 10b5-1 exemption the filing does not support. Wrong dispositions also have asymmetric costs: a missed violation is worse than an extra alert, but alert fatigue is the real price of over-flagging (False positives).

    Regulatory frame: SEC Rule 10b-5, Section 16(a), Rule 10b5-1 and FINRA 3110 (see Regulatory basis).

    Verification¶

    What is checked, and by what:

    Check By Where
    The plan covers every mandatory tool, details first Code check_plan
    Exculpatory factors come from tool results Code graph/evidence.py
    Each claim is supported by the evidence An LLM judge judge_grounding
    Evidence gathered, ordering, real citations, supported exemptions Code graph/trajectory_audit.py
    The reward Code, no LLM evals/rl_env.py

    The process audit runs on every real investigation and is shown on the finding, record-only (D-A2-7). The reward reuses the same function as its trajectory component (D-A2-8).

    The environment¶

    SurveillanceEnv is a Gymnasium environment. Observations and actions are JSON strings, which is what an LLM policy would emit.

    • reset returns the accession number, the tool list with argument schemas and the tool-call budget. It never returns a label, scenario id or name.
    • step takes either a tool call (the real tool runs) or a submit with a disposition, claims that cite tool-call ids, and any exemptions claimed.
    • Unparseable actions, unknown tools and bad arguments cost 0.05 and count toward the budget. Exceeding the budget ends the episode at -0.5.
    • Only the six real tools run; the plan, judge and finding nodes do not.

    What the reference score does and does not show

    The reference reaching 1.00 on all ten scenarios is a consistency check of the environment and reward. The reference reuses the oracle's decision logic and the scenario labels were designed to match it, so it is not a performance claim. The informative column is the other one: every shortcut loses, and each loses for a specific reason.

    Every number here: n=10, labels designed by construction (data/scenarios.py), scorer is the scripted stand-in (evals/oracle.py), model version n/a, no uncertainty computed. n=10 supports no precision claim. The table is deterministic and is regenerated from the code at every commit.

    Scenario ids in the data

    Accession numbers and some party names carry a SCENARIO- prefix (data/scenarios.py). The environment does not return the label, scenario id or name, but a policy trained on it could key on that prefix. This is a verifier demonstration, not a training set.

    Gate¶

    make eval runs the canonical eval and then evals/run_rl.py, in CI on every pull request. It fails if any of these is false:

    • the reference mean is exactly 1.00 and every reference episode ends in a submit;
    • every other policy scores at least 0.5 below the reference;
    • skipping evidence never scores above gathering it for the same answers;
    • no observation contains a scenario id or name.

    A further CI step fails if the generated results file differs from the committed one. The scorer is the scripted stand-in; no live-model number is gated.

    Live-model run (not gated)¶

    The same ten scenarios were run once through the real graph with real models and scored with the same compute_reward (make eval-live, evals/live_run.py). It is not part of make eval and no CI check depends on it.
    n 10 canonical scenarios
    Models gpt-4o-mini-2024-07-18 (plan, investigate, claims), gpt-4o-2024-08-06 (finding, judge)
    Run date 2026-10-29
    Labels designed with the scenarios, as above
    Disposition accuracy 4 of 10
    Mean reward -0.03 (outcome only: 0.09)
    Cost $0.43 in total, about $0.04 per investigation
    Mean latency 33.5 s per investigation
    Uncertainty none computed; n=10 supports no precision claim, and one run varies from the next

    Per-scenario results and every transcript are in evals/recordings/live-2026-10-29/. Two things stand out.

    • The model missed three of the four flag cases by clearing them, which the outcome table penalises hardest. The accuracy figure says nothing about model quality in general: ten cases, one run, one prompt version.
    • The process audit scored 0 on five of ten runs, and for a real reason. In those five the claim extractor cited no tool-call ids at all, so the audit's citation check failed. The grounding judge also marked many claims unsupported (between 1 and 5 per run), and those findings were still published once the two evidence passes were spent, with the unsupported count visible. A record-only audit and a judge that sees only the claims it is given are doing different jobs; here the audit surfaced a weakness in the claim extractor that the grounding report alone did not.

    The recorded transcripts are what a later replay harness would use to replace the scripted stand-in (evals/oracle.py) with real responses. That replacement is not built yet.

    Lessons learned¶

    1. Outcome-only scoring rewards always_flag. It gets 100% flag recall while being wrong on six of ten cases.
    2. Scaling penalties by the trajectory score makes skipping evidence the best strategy when unsure. A wrong answer multiplied by zero is zero, which beats a thorough wrong answer. Penalties are therefore never scaled (D-A2-8).
    3. Harness-building already exposed two scenarios that were trivially passable (Evaluation). The RL gate applies the same discipline to the reward.
    4. The first version of the gate could not catch two deliberate bugs. Breaking the reward so penalties were scaled, or removing the fabricated-id check, both left the gate green: no policy gave a wrong answer without evidence, and the fabricator cited only ghost ids, which a weaker check also zeroes. Adding blind_always_clear and making the fabricator cite one real and one invented id fixed both, and each mutation now fails make eval. A gate that has never been seen to fail is not evidence.
